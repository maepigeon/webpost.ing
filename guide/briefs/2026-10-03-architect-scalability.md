# 2026-10-03-architect-scalability  (Opus architect; read-only on code)
**Owner's words:** "research how to make this scalable too. make considerations on a scalable architecture for my application".
**Context:** webpost.ing is one Spring Boot 3.4 + JdbcTemplate app, PostgreSQL, nginx, uploads on local disk, all on ONE 2 GB DigitalOcean droplet, one maintainer, invite-only today, about to open sign-ups. A second site, webpaint.ing (Godot web client, live multi-user drawing over WebSockets, video), will share the droplet and the accounts (`guide/webpaint-plan.md`; an architect is writing `guide/webpaint-architecture.md` now — read it if it exists when you start, otherwise the plan). Read `guide/performance-review-2026-10-03.md` (current costs and quick wins), `guide/project-structure.md`, `guide/DEPLOYMENT.md`, `guide/CONFIGURATION.md`, `guide/SECURITY.md`, and the code it takes to check your claims.
**What blocks scaling today (verify each in the code and add what you find):** sessions and every rate limiter live in the JVM's memory (one process only; lost on restart); uploads on the local disk; images processed in the request thread; post bodies up to 5 MB in the main table; polling instead of push; in-process scheduled work (email digests); migrations run at start-up by each instance; no CDN; one database with no replica or tested restore; deploys restart the only instance.
**Write `guide/scalability.md`** (the only file you create; do not edit code; use web search if you have it for current prices and limits, and mark anything from memory as to-recheck). Make it a staged plan tied to real thresholds, not an ideal architecture:
1. **Where the ceiling is now**: a rough capacity estimate for the current droplet after the performance quick wins (concurrent users, requests per second, storage growth per active user), the first three things that will break as usage grows, and how to see each coming (what to measure, with the cheapest tooling).
2. **Stage 0, stay on one box well** (now): what to finish (memory caps, caching, indexes, backups with a restore test, monitoring and alerts, a status/maintenance page), vertical resize points and their cost.
3. **Stage 1, two boxes** (database or managed database separate from the app; object storage for uploads behind a CDN): exactly what must change in the code first so this is a configuration change later — a storage interface in front of the upload directory, sessions in the database or Redis behind the existing `LoginRepository` interface, rate limits behind an interface with an in-memory default, background jobs in a table-backed queue, migrations run once by the release rather than by every instance.
4. **Stage 2, several app instances** behind a load balancer: statelessness checklist, sticky sessions vs shared sessions, WebSocket rooms for webpaint.ing (one room per instance with a router, or a small dedicated realtime service), zero-downtime deploys, read replicas, search moved out of `ILIKE`.
5. **Stage 3, only if it takes off**: media pipeline, queues, splitting services; what NOT to build before then, and why.
6. For each stage: the trigger (a measured number), the monthly cost range, the work in days for one developer with AI help, the risks, and what Mae must do herself (accounts, billing, DNS).
7. **Design rules for new code from today** so nothing new makes scaling harder (a one-page list an implementer can follow), and **work packages** for the code-side preparation that is cheap to do now, with disjoint file lists and tests.
8. How the same thinking applies to webpaint.ing (stroke relay, rooms, video storage and egress costs).
Be concrete and frank; prefer boring, proven pieces; one maintainer has to run this. Final reply: the ceiling estimate, the three first breakages, the stage triggers, and the work packages worth doing now.
